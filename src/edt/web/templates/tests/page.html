Comment sont organisés ces tests
{%- if t.famille == "unitaires" %}

Un test unitaire exerce un seul module de l'application, en appelant directement ses fonctions Python. Il n'envoie aucune requête web, ne lance aucune commande ni aucun autre processus : un échec désigne donc directement le module fautif.

Les tests sont rangés par composant (un dossier par partie de l'application), puis par fichier. Chaque test peut avoir plusieurs cas (mêmes vérifications sur plusieurs données) : il est réussi si tous ses cas le sont.

{%- else %}

Un test d'intégration fait travailler plusieurs couches réelles ensemble, sur une base temporaire : une requête web ou une commande traverse les services, la logique (générateur, vérificateur, import et export) jusqu'à la base, ou un calcul complet est mené de bout en bout.

Les six parcours du composant parcours rejouent l'usage réel de l'application, du formulaire « Générer » au fichier iCal exporté. Les autres composants vérifient leurs écrans, leurs commandes et leurs calculs.

{%- endif %}

Les tests tournent à part, sur une base temporaire effacée à la fin : la base de l'application n'est jamais touchée. Les tests de charge, longs, ne se lancent pas depuis le site, seulement par la commande python -m edt tests --test …. Pour laisser le serveur aux autres visiteurs, un court délai sépare la fin d'une exécution du lancement suivant depuis le site.
